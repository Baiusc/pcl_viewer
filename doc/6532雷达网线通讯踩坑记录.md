## 2. 故障排查与深度复盘

---

### 故障一：宿主机 Ping 正常（0.1ms），但 SSH 报错 `Connection reset by peer`

#### 2.1 现象
在 Ubuntu 宿主机上执行 `ping 192.168.137.200` 正常回包，且延迟极低（`0.14 ~ 0.35 ms`）。  
但执行 `ssh root@192.168.137.200` 立即中断：
```text
kex_exchange_identification: read: Connection reset by peer
```
`ssh -vvv` 详细日志显示刚发出 `Local version string SSH-2.0-OpenSSH_8.2p1` 就被掐断，**连服务端的 SSH Banner 均未收到**。

#### 2.2 深度排查
```bash
arp -n 192.168.137.200
# 输出：没有记录

ip route get 192.168.137.200
# 输出：192.168.137.200 dev utun table 1970566510 src 198.18.0.1 uid 1000
```

#### 2.3 根因分析
1. **TUN 虚拟网卡劫持**：主机运行了科学上网客户端（Clash/Mihomo/Sing-box 等），开启了 **TUN 模式（`dev utun`，虚拟源地址 `198.18.0.1`）**。
   * TUN 驱动伪造了 ICMP 回应，导致出现“延时 0.1ms 但 ARP 缓存为空”的虚假连通。
   * 私网 SSH 请求被当成公网流量丢入代理核心，代理核心对私网地址直接返回 TCP RST。
2. **物理网络未配置网段**：Ubuntu 宿主机物理网卡（`enp4s0`）仅有 DHCP 获得的 `10.42.0.229`，完全缺少 `192.168.137.x` 网段，二层物理网络根本未打通。

#### 2.4 解决方案
1. 彻底关闭代理客户端的 **TUN 模式**。
2. 给物理网卡追加临时同网段别名 IP：
   ```bash
   sudo ip addr add 192.168.137.50/24 dev enp4s0
   ```
3. 再次 SSH，顺利弹出 ECDSA 主机指纹确认，输入密码成功登入雷达。

### 故障二：雷达驱动启动，但宿主机接收不到 40Mbps 点云数据

#### 2.1 现象
在雷达端进入目录并拉起程序：
```bash
cd /root/Linux_pcl && sh fsLAA.sh
```
传感器（FL6X32、FL9003、FL9103）均已上电并开始扫描（`start scan`），但宿主机系统监视器中接收速率只有几 KB/s。

#### 2.2 深度排查
在 Ubuntu 宿主机上执行底层抓包：
```bash
sudo tcpdump -i enp4s0 host 192.168.137.200 -n
```
抓包结果仅有周期性的 IEEE 1588 PTP 精确时钟同步多播心跳：
```text
IP 192.168.137.200.319 > 224.0.1.129.319: UDP, length 44
```
*说明物理链路畅通，但雷达完全没有外发高频点云包。*

#### 2.3 根因分析
该雷达采用**单播（Unicast）机制**，内部写死了目标客户端接收端 IP 为 `192.168.137.100`。雷达不是向局域网广播泛洪，而是只向 `.100` 的 MAC 地址定向推送点云。

---

### 故障三：VMware Win11 虚拟机点云流量为 0

#### 3.1 现象
雷达上位机为 Windows 专有软件，在 Ubuntu 宿主机内打开 VMware Win11 虚拟机后，Win11 的网卡吞吐量一直为 0 Kbps。

#### 3.2 根因分析
* VMware 默认采用 **NAT 模式**，Win11 位于宿主机内部创建的虚拟隔离网段（`192.168.68.x`）。
* 雷达发往物理网线上的 `192.168.137.100` UDP 单播报文，宿主机不会自动转发进 NAT 虚拟机。

#### 3.3 解决方案
1. 将 VMware 虚拟机的网络适配器改为 **桥接模式 (Bridged)**。
2. **【关键避坑点】强制绑定物理网卡**：
   在 VMware 菜单栏选择 `编辑` -> `虚拟网络编辑器`，将 `VMnet0` 的桥接目标从“自动”**手动指定为实际插网线的物理网卡 `enp4s0`**（防止被错误桥接到 `docker0` 或 `utun` 上）。

### 故障四：Win11 无法配置静态 IP，Ping 报“传输失败。常见故障”

#### 4.1 现象
在 Win11 中通过界面或 `netsh` 配置静态 IP：
```powershell
netsh interface ipv4 set address name="Ethernet0" static 192.168.137.100 255.255.255.0 192.168.137.1
```
* 执行 `ipconfig` 时，网卡下**完全不显示 IPv4 地址**，或者回退显示为链路本地地址 `169.254.247.198`。
* 执行 `ping 192.168.137.200` 立即报错：`PING：传输失败。常见故障。`。

#### 4.2 深度排查：Windows DAD 机制
在 Win11 PowerShell 中查询网卡接口底层状态：
```powershell
Get-NetIPAddress -InterfaceAlias "Ethernet0"
```
终端输出暴露问题：
```text
IPAddress    : 192.168.137.100
AddressState : Duplicate    <--- 核心元凶：IP 冲突（被系统停用）

IPAddress    : 169.254.247.198
AddressState : Preferred    <--- 回退启用自动私有 IP
```

#### 4.3 为什么 Ubuntu 能设 `.100`，而 Win11 却不行？（OS 差异）
* **Linux (Ubuntu)**：`ip addr add` 属于底层强行绑定命令，默认**不执行 IPv4 主动冲突探测**。即便网络中存在相同的 IP，Linux 也会霸道强占，从而在局域网内形成 ARP 冲突竞争。
* **Windows (Win11)**：严格遵循 RFC 5227 规范，内置 **IPv4 DAD（重复地址检测）机制**。
  1. Win11 激活静态 IP 前，会先向局域网广播免费 ARP（Gratuitous ARP）探测包；
  2. 此时局域网内有设备立即响应；
  3. Windows 判定发生严重 IP 冲突，为保护局域网不陷入混乱，**主动撤销绑定并将该 IP 置为 `Duplicate`**，网卡自动降级回退至 `169.254.x.x`。

#### 4.4 溯源定位局域网冲突源
在 Ubuntu 宿主机上排查谁在响应 `.100`：
```bash
ping -c 2 192.168.137.100
arp -n 192.168.137.100
```
输出：
```text
192.168.137.100  ether  f4:f1:9e:25:44:56  C  enp4s0
```
* 状态为 `C`（Complete），表示真实存在物理设备。
* MAC 前缀 `F4:F1:9E` 指向 PC 制造商 **Wistron InforComm（纬创资通）**。
* 比对最初的调试日志路径 `C:\Users\yx>`，锁定为同事 **杨鑫**（工号/用户名缩写 `yx`）。其电脑此前调试雷达配了静态 `.100`，测试完后网线未拔掉且未改回 DHCP。

## 3. 补充技术扩展：若无法协调改 IP，如何修改雷达硬编码？

在排查过程中，曾在雷达端尝试全局检索配置文件：
```bash
grep -rn "192.168.137.100" /data/ /root/ /etc/
```
结果证实：**雷达固件未提供外部 JSON/INI 配置文件，目标 IP 直接硬编码在 ELF 可执行二进制文件 `/root/Linux_pcl/bin/soc_example` 中**。

### 二进制等长字符串安全替换技巧
* 原字符串：`192.168.137.100`（15 字节）
* 目标字符串：`192.168.137.141`（15 字节）

由于长度完全相同，在 Ubuntu 宿主机上可通过 Python 直接进行无损字节替换，绝不破坏 ELF 节区偏移和符号表：
```bash
# 1. 从雷达拉取二进制程序
scp root@192.168.137.200:/root/Linux_pcl/bin/soc_example ./soc_example

# 2. Python 二进制安全替换
python3 -c "
with open('soc_example', 'rb') as f:
    d = f.read()
new_d = d.replace(b'192.168.137.100', b'192.168.137.141')
with open('soc_example', 'wb') as f:
    f.write(new_d)
print('Replace Success!')
"

# 3. 推回雷达并赋予权限
scp ./soc_example root@192.168.137.200:/root/Linux_pcl/bin/soc_example
ssh root@192.168.137.200 "chmod +x /root/Linux_pcl/bin/soc_example"
```

## 4. 最终解决步骤与闭环指标验证

本次排障采取了最纯粹的根治方式：**协调同事释放冲突 IP**。

### 步骤 1：释放宿主机与外部冲突源
1. 联系同事（杨鑫），将其有线网卡改回 **“自动获得 IP 地址 (DHCP)”**，其电脑恢复分配公司内网 IP `10.42.0.90`，物理地址 `F4-F1-9E-25-44-56` 彻底让出 `.100`。
2. 在 Ubuntu 宿主机上彻底删除之前测试挂载的 `.100`（保留 `.50` 供 SSH 使用即可）：
   ```bash
   sudo ip addr del 192.168.137.100/24 dev enp4s0
   ```

### 步骤 2：雷达端清除残留 ARP 缓存
登录雷达，删除旧的 ARP 绑定：
```bash
ip neigh del 192.168.137.100 dev eth0
```

### 步骤 3：在 Win11 虚拟机中重新应用静态配置
在 Win11 管理员 PowerShell 中执行：
```powershell
netsh interface ipv4 set address name="Ethernet0" static 192.168.137.100 255.255.255.0 192.168.137.1
```
查看状态变迁：
```powershell
Get-NetIPAddress -InterfaceAlias "Ethernet0"
# AddressState 由之前的 Duplicate -> Tentative -> Preferred (正常激活)
```

### 步骤 4：全链路指标验证
1. **连通性测试**：
   在 Win11 中 Ping 雷达：
   ```powershell
   ping 192.168.137.200
   # 来自 192.168.137.200 的回复: 字节=32 时间<1ms TTL=64 (丢包率 0%)
   ```
2. **吞吐量与性能监控**：
   * Win11 任务管理器中，`Ethernet0` 网络吞吐量瞬间平稳拉升至 **`41.3 Mbps`**（约 `5.1 MiB/s`）。
   * 41.3 Mbps 与该型号激光雷达标称的 40 Mbps 吞吐量完全契合。
3. **业务闭环**：打开 Windows 雷达专有上位机软件，点云实时渲染画面平稳流畅呈现。
