> 实施顺序中的该阶段取消。

---

## 0. 结论摘要

1. **方向可行**，你四张图的分层（地址 → 发现 → 会话独占 → 数据面）是正确的工程拆法，不需要推翻。
2. **ACD 必须做**：共享二层下两台同地址会让所有人的 ARP 表打架，流量随机投递到其中一台，表现为“连上了但数据不对/时好时坏”。这是本方案最不能省的一步。
3. **光有唯一 IP 不够**：它只能区分“两台机器”，不能区分“货架上哪一台”。必须把 SN 绑定到名字/TXT，并提供 identify（闪灯/打印）手段，见 6.4。
4. **MAC 已确认稳定唯一**（实测 `28:B5:E8:E2:60:19`，TI 的 OUI，重启不变）—— v0.1/v0.2 说它随机是错的，v0.3 已更正；原“固定 MAC”阶段取消，反而多了一个可用的设备主键。
5. **实现选型要按“30MB 内存盘 + 无 dbus + 无 systemd”来**：不要上 avahi-daemon，建议 mDNS 用单文件库 `tinysvcmdns`，Link-Local 自研（AF_PACKET 构 ARP）。

## 2. 拓扑（已确认，v0.2 修订）

**实际场景是“共享二层”，不是每台独占一个网口：**

```
   工程师 PC-1 ─┐
   工程师 PC-2 ─┼── 交换机 ──┬─ 雷达 1
   工程师 PC-3 ─┘            ├─ 雷达 2
                             └─ 雷达 N
   → 同一广播域；任一台雷达会被所有 PC 同时发现；两台雷达地址相同时，谁都分不清
```

由此确定三条硬性要求：

1. **地址必须全局唯一**，不能靠“物理隔离”逃避冲突 → **ACD（RFC 5227）必须实现**，不能省。
2. **必须能按身份区分设备**：光有唯一 IP 只能区分“两台机器”，不能区分“货架上哪一台”。必须把 SN 绑定到名字、IP、TXT 三处。
3. **必须有会话独占**：两人能看到同一台设备，就可能同时改参数，必须有锁，否则互相打架。

已确认的条件：

| 条件 | 结论 | 影响 |
|---|---|---|
| SN 唯一（每台不同） | ✅ | 可用 SN 派生地址与命名 |
| 调试主机 Windows | ✅ | 多网卡需绑定接口；mDNS 需按接口处理 |
| **雷达固件可修改** | ✅ **已确认** | **走内置锁（7.4 路线 A）**，点云线程直接 connect 到持锁方，零拷贝、无代理 |
| **无交换机管理权** | ⚠️ **已确认** | 不能动 IGMP snooping / 端口隔离 / VLAN / 镜像口；发现机制必须有**不依赖组播**的兜底，排查只能靠两端抓包 |

> v0.1 里把“每台独占网口”当作可能的简化路径，已作废——多台 PC 共用同一网段时，那个前提不成立。

## 3. 总体架构

```
┌──────────────────────── 雷达端（每台） ────────────────────────┐
│  应用层   会话锁 / 点云单播控制   ← TCP 8080（HTTP 或自定义）   │
│           点云输出                 → UDP 单播 (client_ip:2368)  │
│  ─────────────────────────────────────────────────────────────  │
│  发现层   mDNS responder（tinysvcmdns）  名字 lidar-<SN>.local  │
│           记录：A / PTR / SRV / TXT(state, model, sn, fw)       │
│  ─────────────────────────────────────────────────────────────  │
│  地址层   LL 守护进程：SN→地址派生 + ARP Probe/Announce(ACD)    │
│           169.254.<h>.<l>/16，冲突则偏移重试                    │
│  ─────────────────────────────────────────────────────────────  │
│  链路层   固定 MAC（本地管理位置 1，由 SN 派生）                 │
└─────────────────────────────────────────────────────────────────┘
                              │ 二层广播域
┌──────────────────────── 主机侧（PC） ──────────────────────────┐
│  发现：mDNS 浏览 _lidar._tcp → 得到 IP/端口/TXT                │
│  连接：绑定到指定网卡（Linux: SO_BINDTODEVICE；Win: 绑源 IP）    │
│  会话：ACQUIRE_LOCK → 收流 → 心跳续约 → RELEASE                 │
└─────────────────────────────────────────────────────────────────┘
```

设计原则：**下层只负责“能被找到”，上层只负责“谁能用”**。两层解耦，任何一层出问题都能独立定位。

## 4. 阶段 0：MAC 稳定性（v0.3 关闭：已确认没问题）

### 4.1 更正记录

v0.1 / v0.2 里“MAC 每次启动随机生成”的判断是**错的**，依据不足（把 TI 参考设计的常见情况当成了事实），原始启动日志里并没有 `Use random MAC address` 这句。用户实测：

```
eth0: 28:B5:E8:E2:60:19      重启多次不变
```

`28:B5:E8` 是 Texas Instruments 的 OUI（2022-10-26 注册，MA-L），首字节 `0x28` 的 bit0=0（单播）、bit1=0（全局管理）→ 这是**厂商烧写的合法全球唯一地址**，来自核心板 EEPROM 或 SoC eFuse，不是随机值。

**结论：本节作废，不需要改 U-Boot、不需要写 eFuse、不需要启动脚本设 MAC。**

### 4.2 但仍要做一件事：批量唯一性抽查

MAC 稳定只说明“这台不变”，不说明“每台不同”。产线常见事故是 EEPROM 漏烧，整批共用同一个 MAC——那样多台雷达挂同一交换机时，二层直接就乱了，比 IP 冲突更难查。

抽查方法（任选）：

```sh
# 板上读
ip link show eth0 | grep ether
# 或直接读 EEPROM（若硬件有），或看标签与读值是否一致
```

抽 3 台以上上电，确认三台 MAC 互不相同，且与机壳标签上的编号能对应。

### 4.3 顺带的好处

MAC 既然稳定且唯一，它就多了一个用途：**SN 读不到时的备选主键**。地址派生、mDNS 命名都可以退回用 MAC，方案对“SN 是否可读”的依赖降低了。

## 5. 阶段 1：地址层（RFC 3927 + RFC 5227）

### 5.1 地址派生规则（v0.2 修订）

共享二层下，地址必须唯一且可追溯。采用 **SN 派生 + ACD 校验 + 回退链**，而不是纯随机：

```
首选： h = crc16(SN)
       a = 169.254.(h >> 8).(h & 0xFF)
       排除保留段 x.x.0.0/24 与 x.x.255.0/24（命中则 h ^= 0x0101 重算）
序次： 若首选冲突 → 用固定 MAC 派生（crc16(mac[0..5])）
       若仍冲突 → 用 MAC 低 16 位 + 递增偏移，最多 8 次
       8 次全失败 → 退避 60s 后重来，同时置故障标志（日志 + TXT 里 err=no_addr）
```

为什么不是纯随机（RFC 3927 原生做法）：

- 纯随机地址每次上电都变，现场无法贴标签、无法写进工单、日志无法复盘；
- SN 派生后地址**确定**：同一个 SN 永远得到同一个地址，除非被占用；
- 探测仍然要做，但只需 **1 轮（3 次 Probe，间隔 200ms）**即可确认，而不是标准的 4 次 × 1s——因为地址不是猜的，是算的，冲突概率极低。

> 这一点是 v0.2 的关键修订：v0.1 假设“每台独占网口所以可以不探测”，现在必须探测；但因为地址确定，探测成本从 3~10 秒降到 ~0.6 秒。

### 5.2 冲突发生时的行为（必须严格按顺序）

```
检测到冲突
  ├─ 若冲突来自"完全相同的 SN 派生地址"（返修换板、SN 写重）
  │     → 本机立即让位：回退链进第 2 步（MAC 派生），并记录 warn 日志
  │     → mDNS 名字同步改成 lidar-<SN>-2.local
  ├─ 若运行中（已 BOUND）被别的设备抢答 ARP
  │     → 先 Defend（回 2 次 ARP 应答）；仍冲突则判定被强占
  │     → **立刻** mDNS goodbye 旧记录 → 重新选地址 → announce 新记录
  └─ 全程写 syslog，字段：事件、旧地址、新地址、对端 MAC、时间(monotonic)
```

**最容易踩的坑**：地址变了但 mDNS 缓存没刷新。RFC 6762 的 A 记录 TTL 是 120 秒，如果只改地址不 goodbye，工程师的 PC 会在两分钟内继续往旧地址发包，表现为“明明连上了却收不到数据”。所以 **goodbye（TTL=0）必须在换地址之前发出**。

### 5.3 ACD 状态机（RFC 5227）

```
INIT ──选地址──> PROBE ──(发 4 次 ARP Probe，间隔 1s，随机抖动 0~250ms)
                    │
        收到冲突 ARP ──> DEFEND/RESELECT ──(偏移 +1 重算)──> PROBE
                    │
              无冲突 ──> ANNOUNCE（发 2 次 gratuitous ARP，间隔 2s）──> BOUND
BOUND ──收到他人 ARP Probe 询问本地址──> 立即回 ARP 应答（Defend）
BOUND ──连续冲突 3 次 / 10 次重试失败──> 放弃，置错误状态，红灯/日志告警
```

### 5.4 实现选型

| 方案 | 体积 | 依赖 | 评价 |
|---|---|---|---|
| `avahi-autoipd` | ~200KB + 依赖 | 需 avahi 包 | 成熟，但引入 avahi 体系，与"精简"目标冲突 |
| 自研 C（约 300~400 行） | <30KB | 仅 libc + AF_PACKET | **推荐**：完全可控，能内置 SN 派生规则 |
| busybox 脚本 + `arping` | 0 | 无（但系统里没有 arping） | 需要额外加 busybox applet，且时序控制粗糙 |

自研要点：

- 用 `AF_PACKET` 直接构造 ARP（SPA=0.0.0.0 的 Probe，SPA=本地址的 Announce）；
- 设地址用 `ioctl(SIOCSIFADDR)` 或 netlink，busybox 环境没有 `ip addr add` 也无所谓；
- 全程用 `CLOCK_MONOTONIC`，不要用 `time()`（板子无 RTC 电池，时间会从 1970 开始，实测报告里就是 1970）；
- 线程优先级用 `SCHED_OTHER` + nice +10，**不要碰实时优先级**，否则会干扰 PREEMPT_RT 的点云线程。

## 6. 阶段 2：发现层（RFC 6762 / 6763）

### 6.1 命名与记录

| 记录 | 内容 | 说明 |
|---|---|---|
| A | `lidar-<SN>.local → 169.254.x.y` | TTL 120s |
| PTR | `_lidar._tcp.local → lidar-<SN>._lidar._tcp.local` | 服务浏览用 |
| SRV | `port 8080`, `target lidar-<SN>.local` | 控制端口 |
| TXT | `sn=001A`, `model=AT128`, `fw=1.2.3`, `state=FREE/BUSY`, `proto=1` | 状态一眼可见，省一次握手 |

`state` 字段建议实时反映锁状态（FREE / LOCKED），主机侧浏览列表就能看到"哪台正被占用"，减少误连。

### 6.1.1 无交换机管理权 → 必须有不依赖组播的兜底（v0.4）

现场拿不到交换机配置权，意味着 **IGMP snooping 是开是关、有没有 querier，你都不知道也改不了**。组播在这类交换机上的典型表现有三种，且会随固件版本/负载变化：

- 正常泛洪 → mDNS 好用；
- 开了 snooping 但没有 querier → 成员关系表老化，**几分钟后组播突然不通**，重连又好了；
- 只按已知组转发 → 新上电的设备第一次 announce 就丢。

这类"时好时坏"的故障最难查，所以**不能把发现机制全押在组播上**。加一层广播兜底，成本极低：

```
设备侧（上电 + 每 5s）：
  UDP  → 255.255.255.255:5354   {"sn":"001A","ip":"169.254.124.121","state":"FREE","port":8080}
PC 侧：
  监听 0.0.0.0:5354，维护设备表（按 sn 去重，30s 未收到即标记过期）
```

为什么广播更可靠：**广播帧交换机必须泛洪，不受 IGMP snooping 影响**（除非开了风暴抑制，那是另一个阈值问题）。代价是每 5 秒几十字节，可以忽略。

两条通道的分工：

| 通道 | 作用 | 失效时的表现 |
|---|---|---|
| mDNS（组播） | 标准发现、名字解析、跨平台兼容 | 名字解析失败，但广播表里仍有 IP |
| UDP 广播（兜底） | 保证"至少能看到设备列表" | 几乎没有失效场景 |

> 注意：`255.255.255.255` 是受限广播，不跨路由器；跨网段场景不适用——但你们是同网段，正好。

### 6.2 名字冲突处理

RFC 6762 要求先 Probe（查询同名 A 记录）再 Announce。若冲突：

- 第 1 次冲突 → `lidar-001A-2.local`
- 第 2 次 → `lidar-001A-3.local`

同时 TXT 里保留原始 SN，主机侧以 SN 为准，不以名字为准（名字只是给人看的）。

### 6.3 实现选型

| 方案 | 体积 | 依赖 | 评价 |
|---|---|---|---|
| avahi-daemon | ~2MB+ | dbus + expat + glib | 功能全，但把 30MB 系统撑大 10%，且拉起 dbus 又是一套服务 |
| **tinysvcmdns**（单文件，MIT） | ~40KB | pthread | **推荐**，只需实现 A/PTR/SRV/TXT + announce/goodbye |
| 自研 | ~600 行 | 无 | 可控但要自己处理名字压缩、缓存刷新、legacy 查询 |

注意：mDNS 的组播地址 `224.0.0.251:5353`，需要 `IP_ADD_MEMBERSHIP`；发送用 `IP_MULTICAST_TTL=255`。

### 6.4 设备识别（关键补充，v0.2）

共享二层下最真实的问题不是“分不清 IP”，而是：

> 我知道有 `169.254.10.23`、名字叫 `lidar-001A.local`，但**货架上那一排雷达，哪一台是它？**

唯一 IP 只解决了“两台机器不撞地址”，没解决“人和实物对不上”。必须补三件事：

| 手段 | 做法 | 成本 |
|---|---|---|
| **名字带 SN** | `lidar-<SN>.local`，TXT 里再冗余一份 `sn=001A` | 0 |
| **列表带状态** | TXT 实时更新 `state=FREE/LOCKED`、`owner=<持锁方IP>` | 小 |
| **主动识别** | `POST /api/identify {"seconds":5}` → 该机闪灯 / 蜂鸣 / 串口打印大号 ASCII 编号 | 中（需要 GPIO 或串口输出） |

识别接口的设计要点：

- **不受会话锁限制**，任何人都能触发（否则“想找设备”还得先抢锁，逻辑绕）；
- 触发后要在 TXT / status 里标记 `identify_by=<发起方IP>`，避免两人同时在货架前按，互相以为是自己那台；
- 你这块板子当前**没有 LED class**（`/sys/class/leds` 不存在），闪灯要先补 gpio-leds 或直接用 `/sys/class/gpio` 驱动 LED1/LED2（见 2026-10-30 记录：main_gpio0:7 / main_gpio1:49）；
- 没有灯就退化为“串口打印 + 网络侧 status 回显编号”，虽然土但有效。

### 6.5 多工程师并发时的表现

```
PC-A 浏览列表：  lidar-001A.local  169.254.10.23   FREE
                lidar-002B.local  169.254.20.87   LOCKED by 169.254.1.31 (PC-B)
PC-B 正在调 002B，PC-A 看到状态就知道别去碰；即使去连，也会被 423 挡回来。
```

这是“多人共用一套设备”场景下最省事的防呆：**状态外露 + 连接时强校验**，两层都做。

## 7. 阶段 3：会话层（独占锁）

你在图里的设计基本可用，但参数要调：

### 7.1 锁状态机

```
IDLE ──ACQUIRE(client)──> HOLDING(token, client_ip, expiry)
HOLDING ──RENEW(token)──> HOLDING（刷新 expiry）
HOLDING ──超时 / 主动 RELEASE / TCP 断开 + 心跳丢失──> IDLE
HOLDING ──FORCE_UNLOCK(物理按键/长按 5s)──> IDLE
```

### 7.2 参数建议

| 参数 | 你的图里 | 建议 | 理由 |
|---|---|---|---|
| lease_ttl | 3000ms | **5000~10000ms** | 3 秒太紧，一次 GC 或网络抖动就掉锁，现场体验差 |
| 续约周期 | — | lease/3 | 标准做法，容忍两次丢包 |
| Watchdog | 2.8s / 3.0s | lease-1s / lease | 与 lease 联动，不要写死 |
| 单播端口 | 2368（监听 0.0.0.0） | **connect() 到固定对端** | 绑 0.0.0.0 意味着任何源都能发；用 connect 让内核过滤非法源 |

### 7.3 接口（建议 REST 风格，便于抓包和手工调试）

```
POST /api/session/lock     {"client":"169.254.1.101"}  → 200 {"token":"...","lease_ttl":8000}
POST /api/session/renew    {"token":"..."}             → 200 / 410 GONE
POST /api/session/unlock   {"token":"..."}             → 200
POST /api/config/rpm       {"value":600,"token":"..."} → 200 / 423 LOCKED
GET  /api/status                                       → 200 {"state":"LOCKED","owner":"...","rpm":600}
```

关键点：**所有写操作都必须带 token**，未持锁者一律返回 `423 LOCKED`，并在响应体里带上当前 owner IP——现场工程师能立刻知道"是谁占着"。

### 7.4 固件改不改？（决策记录）

“改固件”不是重写算法，实际只有四件小事，而且其中只有一条是硬需求：

| 要做的事 | 必须改固件吗 | 不改固件怎么办 |
|---|---|---|
| 设备地址 / mDNS 名字 | ❌ 完全不用 | 独立守护进程（lladdr、mdns）在用户态跑，跟固件无关 |
| 独占锁（谁在用） | ❌ 不用 | 旁路代理接管控制端口，代理里做锁 |
| **点云只发给持锁方** | ✅ **硬需求** | 代理转发：固件照旧发，代理收到再按锁状态转给持锁方（多一次拷贝 + 0.x ms 延迟） |
| identify（闪灯/打印） | ❌ 不用 | 代理直接操作 gpio sysfs 或写串口 |
| 参数写保护 | ✅ 建议 | 代理拦截写请求，校验 token（要求控制通道走 TCP 且经过代理） |

**结论（v0.4 已定：走内置）**

固件已确认可改，采用**内置锁**：

- 点云线程在持锁后直接 `connect()` 到客户端 (ip, port)，零拷贝、零额外延迟、无代理单点；
- 锁、identify、TXT 状态、参数写保护全部在固件进程内，不需要第二个进程看护；
- 仍然建议保留一个**只读的旁路诊断**（不改固件也能跑）：`tcpdump` + 设备侧日志推送，用于现场取证。

旁路代理仅作为"以后遇到闭源型号"的备选，本方案不实现。

### 7.5 固件侧改造清单（内置锁）

只动四处，都在应用层，不碰点云算法与实时性关键路径：

| # | 位置 | 改动 | 注意 |
|---|---|---|---|
| 1 | 控制服务（TCP 8080） | 新增 5 个接口：lock / renew / unlock / status / identify | 放在**非实时线程**，不要挂到点云线程的事件循环里 |
| 2 | 点云发送 | 发送目标从常量改为 `session.client_ip:port`，用 `connect()` 固定对端 | 只在持锁时启动发送；释放后立即停发并 `shutdown()` |
| 3 | 定时器 | 用 `CLOCK_MONOTONIC` 判断 lease 到期，周期 200ms 检查 | **不要用 `alarm()`/`SIGALRM`**，会干扰 RT 线程；不要用 `time()`（板子无 RTC，时间是 1970） |
| 4 | 状态输出 | 把 `state/owner/sn` 写到一块共享内存或 `/tmp/state.json`，供 mDNS 守护进程读取 | 不要为了这个让固件直接发 mDNS，职责分离 |

线程模型建议：

```
点云采集线程（RT，不动）
      │ 写入环形缓冲
点云发送线程（普通优先级）── 读 session 快照 ──> sendto 持锁方
      ▲
控制线程（普通）── 锁状态机 ──> 更新 session 快照（原子指针切换）
      │
      └── 每 200ms 检查 lease 是否过期
```

关键：**session 用原子指针切换**（读侧不加锁），避免控制线程持锁时阻塞发送线程。RT 系统里最忌讳的就是在发送路径上加互斥量。

**备选路线的前提校验**（仅当以后遇到闭源型号才用）：旁路代理要能拿到点云流。若固件硬编码发往组播地址，代理加该组播组成员即可收到；若发往固定单播 IP，则需要板上有第二个地址或 iptables 重定向。动手前先 `tcpdump -i eth0 -n udp port 2368` 确认。

## 8. 阶段 4：数据面（点云单播）

- 默认不推流：上电后点云线程挂起，`ACQUIRE_LOCK` 成功才启动；
- 目标地址 = 持锁客户端的 IP + 客户端上报的端口，用 `connect()` 固定对端；
- 锁释放后 **立即停止发送**，并清理 socket；
- 包大小控制在 MTU 内（建议 ≤1400B），避免 IP 分片；
- 带宽核算：单台 120Mbps 时，8 台 = 960Mbps，**千兆交换机已经跑满**。多台并发必须考虑：
  - 每台限速（10/20/40Mbps 可选）；
  - 或按需只开 1~2 台；
  - 或上万兆/多网口分流。

这一条容易被忽略：Link-Local 解决了"找得到"，但没解决"带宽够不够"。

## 11. 风险清单与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| **批量 MAC 重复**（EEPROM 漏烧） | 多台同 MAC 挂同一交换机，二层直接乱，比 IP 冲突更难查 | 抽 3 台以上核对；产线把"读 MAC 与标签比对"纳入工位 |
| **地址变更后 mDNS 未刷新** | PC 继续往旧地址发包，表现为“连上但没数据”，持续 2 分钟 | 换地址前必须先发 goodbye（TTL=0），再 announce 新记录 |
| **两台设备 SN 相同**（返修/写重） | 地址与名字同时冲突 | 回退链 + 名字加 `-2`；同时日志告警，产线应禁止重复 SN |
| **多人同时调试同一台** | 参数被对方改掉，数据异常 | 会话锁 + TXT 外露 owner；写操作一律校验 token |
| 根文件系统在内存盘 | 现场改的配置重启即丢 | 配置写进镜像；或加只读 squashfs + overlay |
| 无 systemd | 守护进程无人看护 | 自写 `S99lidar` 脚本 + 简易 supervisor（`while true; do ...; done &`） |
| 交换机 IGMP snooping（无管理权，改不了） | mDNS 发现时好时坏，几分钟后"突然找不到" | 不依赖组播的 UDP 广播心跳兜底（6.1.1）；PC 端列表以广播表为准，mDNS 只做名字增强 |
| Windows 防火墙 | 5353/UDP 入站被拦 | 安装包时加防火墙规则，或在工具里提示 |
| `mem=511M` | 多路点云缓冲不足，OOM | 放开到 `mem=1900M`；或严格限流 |
| RTC 无电池、时间为 1970 | 证书/TTL/日志时间全错 | 全部用 monotonic clock；日志用相对时间戳 |
| 实时内核 + 组播线程 | mDNS 抖动影响点云实时性 | 网络线程降优先级，绑到非关键核（`taskset`） |
| 30MB rootfs | 加 avahi/dbus 体积翻倍 | 用 tinysvcmdns + 自研 LL，总增量控制在 100KB 内 |

### 14.1 三个只有实测才会暴露的坑

**① 设备侧发广播需要可用出口路由**
改成 link-local 后设备只剩 `169.254.0.0/16` 一条链路路由、**没有默认路由**，此时
`sendto(255.255.255.255)` 直接返回 `ENETUNREACH`，包根本没出去（表现为设备日志正常、PC 什么都收不到）。
修法：`SO_BINDTODEVICE` 绑定网卡，并**同时**发 `169.254.255.255`（匹配 /16 直连路由）。

**② 阻塞 socket 会卡死整个事件循环**
mDNS socket 若为阻塞模式，主循环"读干净队列"的写法读完真实包后会永久阻塞在 `recvfrom`。
设备还会收到自己发的组播，于是**启动即自锁**：广播停发、TCP 能握手但永不 accept
（客户端表现为 `Read` 超时而非拒绝连接——这个特征可用于快速定位）。
修法：所有被 drain 的 socket 必须 `O_NONBLOCK`。

**③ PC 侧入站策略可能一刀切**
本次调试机存在安全软件规则 `codex_sandbox_offline_block_inbound`
（Inbound / Block / Program=Any / 远程地址覆盖所有非环回），优先级高于端口 Allow 规则，
导致广播全部被丢弃，而 PC→设备方向的 ping/scp/TCP 一切正常。
**这决定了产品必须保留"已知 IP 直连"的兜底路径**（对应 `lidar_ctl.ps1 -Ip`），
不能用广播发现作为唯一入口。

### 14.2 测试顺序上的一个陷阱

验证 ACD 时必须先让**设备彻底放弃该地址**（`ip addr flush dev eth0` 或重启），
再让 PC 占用；否则 Windows 在添加静态地址时会先做免费 ARP 探测，
被设备抢先应答后会把该地址标记为"重复地址"并停用，导致后续探测无人应答，测不出冲突。
