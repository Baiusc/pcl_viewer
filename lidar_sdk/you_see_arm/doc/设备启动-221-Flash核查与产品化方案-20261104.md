# 221 Flash 启动核查与产品化方案

核查日期：2026-11-04。范围为 10.42.0.221；第三分区使用 JFFS2 只读挂载。没有执行 Flash 中的安装脚本，没有修改 Flash 文件、停止采集、切换模式或重启设备。检查结束后恢复为未挂载状态。

## 结论与当前设备状态

保留 BusyBox init，替换 `S99user → app_startup.sh → 遍历 install.sh → 后台启动 you_see` 这条产品启动链。系统服务采用明确的服务入口；`lidar_mgrd` 作为独立受监督服务运行，并成为采集应用的唯一启动者。模式由其持久状态和运行配置决定。

221 本次检查前已重新启动，`/tmp/beta-test` 和新管理 CGI 均已消失，当前是原 `/root/you_see`，PID 190。此前上位机验收通过的是 RAM 临时版本，不能据此认为新架构已经进入 Flash 或开机流程。

BusyBox init 本身适合继续使用。[Buildroot 官方说明](https://buildroot.org/downloads/manual/manual.html#_init_system)把它作为默认 init 方案，并提供标准服务脚本规范。需要改造的是产品入口、服务生命周期和文件归属。

## 1. 实际启动链

```text
内核：root=/dev/ram0
  → /sbin/init（BusyBox v1.36.1）
  → /etc/inittab
  → /etc/init.d/rcS
  → 按文件名顺序执行 /etc/init.d/S??* start
  → S99user
      → 挂载 mtdblock2 到 /mnt/mtdblock2
      → chmod 并执行 Flash/app_startup.sh start
          → 将日期设置为 2030-01-01
          → 读取 Flash/mode，缺失时写入 point_cloud
          → 点云时执行 demo_i2c_motor
          → 从对应模式目录 insmod *.ko、复制 *.so 到 /usr/lib
          → 复制 interfaces、启动网络、ping 固定地址、修改并启动 sshd 脚本
          → 遍历 Flash 各子目录，执行其中的 install.sh
              → linuxptp：复制配置和启动脚本，启动 PTP 及其监控
              → you_see_arm：配置复制到 /etc，应用复制到 /root
              → web：解压 www*.tar.gz 到 RAM 根目录，启动 lighttpd
          → /root/you_see &
      → sync，卸载 mtdblock2
```

关机时，`rcK` 按相反顺序调用各服务的 stop，然后卸载文件系统。但是 `S99user` 的 stop/restart 和 `app_startup.sh` 的 stop 都只输出 `ok`，没有执行采集服务的实际停止。

## 3. 现有脚本不满足的条件

| 实际行为 | 对当前目标的影响 | 改造要求 |
|---|---|---|
| Flash/mode 选择底层文件，应用主配置另有 work_mode | 存在两份独立的模式来源，可能搭配错误 | 由管理服务依据已确认状态和平台兼容关系生成一次运行配置 |
| 启动后卸载整个 user 分区 | 管理服务无法持续保存切换事务和用户设置 | 持久存储在运行期间保持可用，正常关机先停服务再卸载 |
| 每次开机把主配置复制到 /etc | RAM 中改动重启后丢失；缺少默认值与用户设置边界 | 默认配置随发布包，用户设置保存到独立持久目录 |
| 扫描所有一级目录中的 install.sh | 新增、备份或遗留目录也可能被当作启动组件 | 只启动明确启用的服务，包内资产按清单安装 |
| 直接后台运行 /root/you_see | 没有交给 lidar_mgrd；不能形成唯一管理入口 | 服务监督器启动 mgrd，mgrd 启动采集应用 |
| stop/restart 不实际工作 | 无法可靠维护、重启服务和有序关机 | 正确等待进程退出，处理超时并返回真实结果 |
| insmod、复制、安装等缺少统一失败处理 | 可能混用旧应用、新库或未成功加载的模块 | 校验配套并逐级检查错误，失败时停止采集启动 |
| 网络、SSH、PTP、Web 和采集安装揉在一起 | 采集维护和系统服务互相牵连 | 各自拥有启动/停止入口和清晰顺序 |
| 固定日期 2030、ping 10.42.0.169、运行时 sed 改 sshd | 引入环境依赖，日志时间失真，启动行为难复现 | 由时间同步和网络服务负责各自配置，不依赖某台开发电脑 |

`S99user` 还提供 `appstop` 内核参数分支，但它跳过整个 Flash 应用入口，网络和 SSH 的部分准备也随之被跳过。正式维护模式应保留基础联网和诊断能力，只停止采集服务。

## 4. 选定的产品启动结构

采用 **BusyBox init + Buildroot 风格系统服务 + runit 服务监督 + lidar_mgrd**。继续使用当前 PID 1；runit 只作为服务监督工具，负责 mgrd 进程的启停和异常退出后的处理。`lidar_mgrd` 负责采集应用及模式事务；两者不重复监督同一个采集进程。

[runit 官方文档](https://smarden.org/runit/useinit)明确支持在保留现有 init 的情况下接入服务监督。[runsv 文档](https://smarden.org/runit/runsv.8)定义了服务启动、退出监督和 down 控制。它的进程重启能力不等于雷达业务恢复成功，业务失败仍必须遵守 mgrd 的回滚次数和 FAULT 状态。

实测当前 BusyBox 只有 init、start-stop-daemon 和 watchdog，**没有 runsv/runsvdir/sv**。所以此方案需要系统裁剪同事将监督工具纳入下一版系统镜像；当前设备不能直接照搬运行。新增体积需以交叉构建结果核算。`start-stop-daemon` 可用于普通服务启停，但不提供持续异常重启监督。

```text
BusyBox init
├── 系统初始化：持久分区、设备节点、可信启动环境
├── 网络 / SSH / PTP 等明确的系统服务
├── Web 服务 → CGI → /run/lidar/control.sock
└── runit 服务监督
    └── lidar_mgrd（前台运行）
        ├── 签名包、平台白名单、模式持久状态
        ├── 平台适配器：电机、驱动与已支持的硬件初始化
        └── you_see（统一应用 + 单一 liblidar.so）
```

启动顺序：存储与可信配置就绪 → 网络与诊断服务就绪 → 验证选定发布包 → 启动 mgrd → 恢复模式和初始化硬件 → 启动采集 → 数据验证后提交。Web 不必等待采集成功；管理服务未就绪时，CGI 返回明确不可用状态。

停止顺序：停止接受新的管理写操作并取消服务自动拉起 → 请求 mgrd 优雅停止应用 → 确认管理与采集进程退出 → 停止其他依赖服务 → 同步、卸载持久分区。不能仅 kill mgrd 后立刻宣布硬件停采。

持续崩溃时需延迟重试并熔断，不能直接配置无限快速重启。业务进入 FAULT 时，mgrd 应继续提供诊断；监督器不能把 FAULT 当作理由重置状态、循环拉起采集。监督目录和 PID/FIFO 放在 RAM，避免持续写 Flash。

服务配置落在系统镜像的 rootfs overlay 或对应 Buildroot 包中，不再通过 Flash 安装脚本动态修改 `/etc/init.d`。具体 SNN 编号根据网络、存储和现有 PTP 依赖确定，不照抄通用发行版的 inittab；BusyBox 的格式与 SysV 存在差异。

## 5. 发布文件与可变数据的布局

以下是拟实施布局，尚未部署：

```text
系统镜像：
  BusyBox init、固定启动入口、监督工具、可信验签工具及公钥

/mnt/mtdblock2/lidar/
├── releases/<release-id>/
│   ├── bin/                        mgrd、采集程序及配套工具
│   ├── lib/liblidar.so              同机型完整功能的用户态库
│   ├── assets/                     明确配套的驱动和板级资源
│   ├── web/                        Web/CGI 发布资产
│   ├── conf/                       出厂默认值
│   ├── manifest.json
│   └── manifest.sig
├── current                         当前发布版本的激活指向
├── config/                         用户持久设置、可信设备配置
├── state/                          模式事务与最后已确认模式
└── calibration/                    与软件升级分开的设备标定数据

/run/lidar/                          socket、临时配置、PID、监督状态
```

模式切换只改变 state 和运行配置，不改变 current、不复制或改名发布文件。换软件版本时才更新激活指向，且必须先停止旧服务、完整验证新包，禁止覆盖正在使用的版本目录。运行实例应固定到已经解析和验证的版本路径，防止后续指向变化造成文件混用。

从包内执行 mgrd 之前必须由系统预置的可信入口完成验证。不能先执行任意上传包里的管理程序，再依赖它自验来建立初始信任；也不能允许上传包同时替换系统的信任公钥和验证工具。

Web 资产可以保留“已验证后展开到 RAM”的方式，符合当前 RAM 根文件系统。重点是固定版本和安装路径、在启动前校验、通过独立服务启动，而不是强制所有东西从 Flash 原地执行。校验失败时保留系统网络和诊断入口，不继续启动采集。

默认使用当前 user 分区承载应用和状态；不因整理目录就改分区表。是否同时保存新旧两套应用版本，以最终包大小、暂存需求和余量核算决定；本次容量检查不足以承诺整机 A/B 升级。

## 6. 下一步开发目标

第一阶段交付 **Beta 固件启动集成包**，供系统裁剪同事纳入镜像：

1. rootfs overlay / Buildroot 集成说明：挂载、网络与诊断、监督工具及有序关机入口。
2. 明确的 mgrd 服务定义和启停入口，替换直接运行 /root/you_see 的链路。
3. Beta 发布安装布局与可信引导校验，复用现有 manifest；不再依赖 /tmp/beta-test 和开发测试公钥。
4. 持久的配置与事务目录、首次启动初始化和重启恢复；后续启动不得清空旧状态。
5. 第一阶段仍只开放固定点云布局的 work_mode 1/2，复用已验收的 HTTP 契约。

验收包括：开机自动启动；切换到 1/2 后重启恢复对应已确认模式；服务正常 stop 后不被监督器立即拉起；重复 start 不产生双实例；mgrd 崩溃和硬件恢复遵守有限恢复策略；存储或签名异常时保留诊断能力；旧启动入口不会再次启动采集程序。

当前 am6204 的硬件停采接口仍未执行真实硬件操作，221 适配器也只用于已知点云布局重开。因此正式硬件停采、复位和其他模式配套仍须驱动同事确认，本次启动整合不把它们视为已完成。电机初始化应纳入经过核对的平台启动步骤，不能在删旧脚本时遗漏。
