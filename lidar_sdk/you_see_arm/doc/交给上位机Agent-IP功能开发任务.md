## 本次实现范围

- 选择电脑网卡；接入 `_lidar._tcp.local.` DNS-SD 与 UDP 5354 广播发现，保留原有采集发现与数据协议。
- 按 MAC 和本机接口作用域合并设备，显示真实 SN 或临时身份、IP、来源、可达性、恢复/故障/模拟状态。
- 支持 `auto`、`pool`、`static`。池配置包含起止地址、掩码和可选网关；由设备探测并选择范围内地址，上位机不自行分配。
- 使用 `GET/POST /cgi-bin/lidar_network.cgi`，接入只读 `/cgi-bin/lidar_network_status.cgi` 诊断入口。不要重新实现设备 CGI。
- 完成“提交一次 → 保存任务关联 → 继续发现与查询 → 连接新 IPv4 → 校验身份和任务 → 确认一次 → 验证保存结果 → 恢复采集”的完整流程。
- 与现有模式切换 UI 协调，避免同设备并行进行模式切换与网络设置。

第一版只做单设备写操作、多设备只读发现；不做批量写 IP、SN 烧写、固件升级、完整设备租约锁或自动更改电脑网卡设置。

## 必须遵守的接口行为

1. `auto` 请求只带 mode；static 和 pool 按对应字段白名单构造。HTTP 不接受 query、`via_address`、`legacy`、自定义程序路径或额外客户端任务号。
2. 202 只是受理。`phase=READY` 和 `ready=true` 也可能仍处于 WAIT_CONFIRM；保存成功要核对 pending、transaction_phase、operation_code、目标配置、设备身份和任务号。
3. 正常路径在确认窗口内通过设备新 IPv4 发送 network_confirm。任务号来自 202；CGI 自行验证实际到达的本机地址。
4. 设置 POST 超时不能自动重发；没有拿到任务号时，不能只因配置相同就认领和确认当前任务。没有公开幂等键、历史任务查询、取消或独占锁接口。
5. 保留 `requested_config`，回滚时不能让设备的 desired_config 覆盖原请求。网络 epoch 改变时停止旧的自动确认。
6. 同 generation 不代表快照相同；COMMITTED 变化不保证计数递增。广播没有完整事务和 epoch，成功判断必须使用新鲜 HTTP 快照。
7. 设备恢复地址只用于管理，recovery=true 或 configuration_valid=false 不属于目标业务配置成功。错误响应可能只有 code/message，或是模式管理形状，不能硬解析成完整网络快照。
8. IP 改变后复用既有采集协议重新握手，收到正确设备的有效数据后，再显示数据连接恢复。

## 开发与验收顺序

1. 写出目标仓库内的具体修改位置，建立配置、设备身份、连接作用域及任务数据模型。
2. 实现 HTTP 封装、参数校验与配置规范化，使用报文样例完成成功、冲突、回滚、响应丢失和外部任务测试。
3. 接入真实异步发现与所选网卡绑定，防止切换设备后的迟到响应污染界面。
4. 接入界面和采集会话，完成开发指导第 10 节中的模拟验收场景。
5. 由用户或设备侧明确提供专用测试设备与部署状态后，再进行实机联调并如实记录未测项。

至少测试：重复 SN、无 SN、多网卡、mDNS 与广播分别失效、池耗尽、READY 但未确认、POST 丢响应不重发、他人相同目标、任务号变化、epoch 变化、同 generation 的提交变化、确认超时、回滚旧地址冲突、故障诊断、错误体缺字段、页面/设备切换、模式切换互斥和采集恢复。

不通过 SSH、root 密码、旧 CGI 或直接编辑设备配置文件补救产品流程；不从客户端调用设备内部 network_apply、DHCP 回调或模拟操作；不自行部署镜像、重启或写入历史设备。遇到设备端缺口，保留最小复现和接口响应，列为联调依赖。

完成后交付代码、构建与运行步骤、测试结果和实机待测清单；明确“客户端模拟”“设备模拟”“实机”三类证据。不要只提交界面，也不要用模拟广播或硬编码 SN 冒充实际设备发现。
