# 固件版本标识指令协议 (0x0302 查看系统固件版本)

> 版本: v1.1
> 日期: 2026-10-10
> 适用: 全部机型 (CS96-alpha / CS96-beta / MF150-fl6031 / MF150-fl6532), 指令通道 V1 协议
> 面向对象: 上位机软件开发者 (查询固件身份与各组件版本, 用于版本追溯)
> 板端实现: `ys_business/ys_business_sys.c` 的 `get_sys_version()`
> 版本来源: `scripts/gen_version.sh` 在构建期从 git 自动注入, 全流程无需人工维护
> 参考实现: `scripts/version_query.py` (Python, 已与板端 CRC 实现实测比对)

---

## 1. 背景

原协议中 `0x0300 查看FPGA固件版本` 与 `0x0302 查看系统固件版本` 两条指令的应答均为
`ret_code(1B) + version uint8_t[3]`(共 4 字节), 只能表达主/次/修订号, 无法承载提交号、
本地改动标记与构建时间; 且二者对"固件"与"组件"的划分已不适用。

**自本版本起:**

1. `0x0300` **废弃**, FPGA 版本作为组件列表中的一行上报;
2. `0x0302` 应答扩展为 **固件总包 + 各组件版本列表**, 载荷 4 字节 → 200 字节;
3. 新增版本标识由**四个维度**共同确定, 缺一不可。

> ⚠️ **这是对本已发布指令的破坏性变更**: 0x0302 的应答载荷长度与结构均已改变,
> 旧上位机必须同步修改。0x0300 已不再注册, 请求会收到 `ret_code=0x01` (非法指令)。

### 1.1 四个维度

| 维度 | 字段 | 作用 |
|---|---|---|
| git 短 sha | `git_sha` | 定位源码提交, 回答"这是哪个代码节点" |
| **本地改动标记** | `dirty` | **最重要**: 为 1 表示该二进制由带有未提交改动的源码构建, 无法由任何提交复现, **不可用于正式发布或验收** |
| 构建时间 | `build_time` | 回答"这是哪一次构建", 同一提交的多次构建靠它区分 |
| 协议版本 | `proto_*` | 兼容性契约, 与固件版本解耦, 不随固件发版每次变化 |

`dirty` 与 `git_sha` 由构建主机上的 `git status --porcelain --ignore-submodules=all` 判定,
**只统计本应用自身的改动**: 各子模块自带版本, 子模块脏不会把本应用标记为不可复现。

## 2. 帧格式

沿用 V1 协议帧:

| 偏移 | 大小 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `sof` | 固定 `0xAA` |
| 1 | 1 | `version` | 协议版本, **必须为 `0x01`** |
| 2 | 2 | `length` | 数据段长度, 小端 |
| 4 | 1 | `cmd_type` | `0x00`=CMD, `0x01`=ACK, `0x02`=MSG |
| 5 | 2 | `seq_num` | 数据段序列号, 小端 |
| 7 | 2 | `crc_16` | 包头校验码, 小端 |
| 9 | n | `data` | 数据段: `cmd_set` + `cmd_id` + 载荷 |
| 9+n | 4 | `crc_32` | 数据段校验码, 小端 |

**校验算法** (与 `core/ys_base.c` 一致):

- `crc_16`: Modbus CRC16, 初值 `0xFFFF`, 反射多项式 `0xA001`, 不取反, 覆盖包头**前 7 字节**
  (即不含 `crc_16` 字段自身)。
  ⚠️ 板端返回的是 `(高字节<<8 | 低字节)`, 再以小端写入报文; 若用常见库计算, 需交换高低字节后再打包,
  否则板端校验不通过、帧被直接丢弃。
- `crc_32`: 标准 CRC-32 (`zlib.crc32`), 初值 `0xFFFFFFFF`, 反射多项式 `0xEDB88320`, 结果取反,
  覆盖**整个数据段**(`cmd_set + cmd_id + 载荷`)。

> 请求方的帧头 `version` 必须为 `0x01`: 板端 `pack()` 按该字节选择应答的编解码版本,
> 非 `0x01` 时不会回包(静默丢弃)。

## 4. 0x0302 应答

数据段 = `cmd_set`(1B) + `cmd_id`(1B) + 载荷(200B), 载荷 = 头部(40B) + 5 × 组件记录(32B)。
**多字节整数均为小端**, 结构体按 1 字节对齐。

### 4.1 头部 (偏移 0~39): 固件总包

| 载荷偏移 | 数据段偏移 | 大小 | 字段 | 说明 |
|---|---|---|---|---|
| 0 | 2 | 1 | `ret_code` | `0x00` 成功 / `0x03` 获取失败 |
| 1 | 3 | 1 | `component_count` | 后续组件记录条数(当前恒为 5) |
| 2 | 4 | 1 | `fw_major` | 固件总包 主版本号 |
| 3 | 5 | 1 | `fw_minor` | 固件总包 次版本号 |
| 4 | 6 | 1 | `fw_patch` | 固件总包 修订版本号 |
| 5 | 7 | 1 | `reserved0` | 预留, 填 0 |
| 6 | 8 | 16 | `product[16]` | 产品名, ASCII, NUL 结尾, 如 `MF150-fl6532` |
| 22 | 24 | 16 | `release_id[16]` | 发布标识, ASCII, NUL 结尾, 如 `20260921-000` |
| 38 | 40 | 2 | `reserved1[2]` | 预留, 填 0 |

固件总包三段版本取自构建时的 `v1.2.3` 形式 git tag; 无 tag 时退化为 `0.0.0`, 由 sha 定位。
`release_id` 默认派生为 `YYYYMMDD-<距最近固件 tag 的提交数>`, 可被 CI 环境变量覆盖。

### 4.2 组件记录 (偏移 40 起, 每条 32B)

| 记录内偏移 | 大小 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `id` | 组件 ID, 见 4.3 |
| 1 | 1 | `valid` | `1`=版本有效 / `0`=尚未接入(占位) |
| 2 | 1 | `major` | 该组件 主版本号 |
| 3 | 1 | `minor` | 该组件 次版本号 |
| 4 | 1 | `patch` | 该组件 修订版本号 |
| 5 | 1 | `dirty` | `1` = 该组件源码有未提交改动 |
| 6 | 1 | `sha_len` | `git_sha` 有效长度; `0` = 无 git 信息 |
| 7 | 12 | `git_sha[12]` | git 短 sha, ASCII, 不足补 `0` |
| 19 | 4 | `build_time` | 构建时刻 UTC Unix 秒, **低 32 位** |
| 23 | 4 | `build_time_hi` | 构建时刻 UTC Unix 秒, **高 32 位**(2038-01-19 前恒 0) |
| 27 | 5 | `reserved[5]` | 预留, 填 0 |

**重要语义:**

- **`sha_len == 0` 时 `dirty` 不可信**: 无 git 信息意味着该二进制来源不可追溯, 上位机应显示
  "未知来源"而非"干净"。切勿把 `dirty=0` 当作"已确认干净"。
- **`build_time` 采用 64 位语义拆分**: 低 32 位在 `build_time`, 高 32 位在 `build_time_hi`。
  2038-01-19T03:14:08Z 之前 `build_time_hi` 恒为 0, 只用低 32 位即可; 之后必须拼接:
  `时间戳 = build_time | (build_time_hi << 32)`。采用无符号存储, 避免有符号 32 位在 2038 回绕。

### 4.3 组件 ID

| ID | 组件 | 当前状态 |
|---|---|---|
| 0 | you_see 应用(总成) | **已接入**, `valid=1` |
| 1 | ARM 驱动 | **已接入**, `valid=1`; 库未提供版本接口或未注入版本时退回占位 `valid=0` |
| 2 | 算法 | 占位, `valid=0` |
| 3 | FPGA | **已接入**, `valid=1`; 寄存器读失败或值非法时退回占位 `valid=0` |
| 4 | Web 服务程序 | 占位, `valid=0` |

记录顺序与 ID 一致。**固定上报 5 条**而不是只报有效条数, 便于上位机直接列出"哪几个组件尚未接入"。
算法 / Web 服务程序两个组件待各自版本方案就绪后填入并置 `valid=1` 即可, **报文格式不变, 上位机无需改动**。

各组件版本来源:

- **you_see 应用(总成)**: 构建期从 git 注入(见第 5 节), 四维身份完整。
- **ARM 驱动**: 取 `liblidar.so` 构建期注入的版本标识(即驱动子模块自身的 git 身份),
  字段语义与 you_see 相同。部分机型的预编译库尚未提供版本接口, 此时该条保持 `valid=0`;
  库更新后无需改动应用代码即自动生效。
- **FPGA**: 运行时经驱动 `lidar_version_get()` 读 0x3000~0x3010 版本寄存器, 字段映射见 4.4。

### 4.4 FPGA 组件记录的字段映射

FPGA 版本来自 5 个 32 位寄存器, 编码为 BCD:

| 寄存器 | 值示例 | 含义 | 映射到组件记录 |
|---|---|---|---|
| 0x3000 版本日期 | 0x20250910 | 小端 BCD, 逐字节 日/月/年低两位/世纪 → 2025-09-10 | 与时刻合成 Unix 秒 → `build_time` / `build_time_hi` |
| 0x3004 版本时刻 | 0x143000 | 小端 BCD, 逐字节 秒/分/时 → 14:30:00 | 同上 |
| 0x3008 版本号 | 0x143000 | 大端 BCD 三段 → 14.30.00 | `major`=14 / `minor`=30 / `patch`=0 |
| 0x300C 版本 hash | 0x1a2b3c4d | 32 位构建 hash | 转 8 位十六进制文本 → `git_sha`, `sha_len`=8 |
| 0x3010 修改状态 | 0 / 1 | 1 = FPGA 有修改 | `dirty` |

**FPGA 行的特殊语义** (上位机解析时注意):

- `git_sha` 存放的是 FPGA 构建 hash 的十六进制文本(8 字符), 而非 git 提交号;
- `build_time` 是 FPGA 的编译时刻(对应组件记录"构建时间"语义), 其字段布局同 4.2 的 64 位拆分;
- 任一寄存器读失败(`0xFFFFFFFF`)、BCD 非法或五个值全 0(FPGA 侧未实现)时, 该条记录 `valid=0`;
- 除上述三点外, 字段位置与展示方式与其他组件完全一致, 上位机无需为 FPGA 特判结构。

## 5. 版本串格式

板端启动日志与 D-Bus(`lidar.get.version`)使用同一格式的完整标识串(该串**不在**本指令报文中,
上位机可用 `fw_*` / `git_sha` / `dirty` / `build_time` 自行拼装):

```
有 git 且干净 : 1.2.3-38da7cf-1758400000
有 git 但脏   : 1.2.3-38da7cf-dirty-1758400000
无 git 信息   : 1.2.3-nogit-1758400000
```

## 6. 与配置文件的关系

`/etc/ys_conf.ini` 中原 `[protocol] version` 配置项已**删除**: 协议版本现以编译期从
`proto-v1.2.3` 形式 git tag 取得的常量为唯一来源。

此前该配置项用于构造广播包, 且一旦被写成非 `1` 的值, 广播包构造会走 `default` 分支导致
**广播长度为 0、广播静默消失、上位机再也发现不了设备**; 改用编译期常量后该隐患已消除。
存量设备 ini 中残留的 `version` 键无人读取, 无害。

## 8. 参考实现与自检

见 `scripts/version_query.py`, 用法:

```bash
python3 scripts/version_query.py <设备IP> [设备指令端口, 默认65000] [本机接收端口, 默认50026]
```

脚本会按正确顺序完成握手(0x0002)与查询(0x0302), 解析并逐字段断言。其 CRC16/CRC32 已与板端
C 实现实测比对一致。

> 注意: **必须先发 0x0002 握手**。板端的 `respond_command()` 在未与上位机建立连接时不会发包,
> 直接发查询指令将收不到任何应答。
