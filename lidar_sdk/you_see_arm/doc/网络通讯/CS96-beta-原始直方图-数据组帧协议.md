# CS96-beta 原始直方图数据组帧协议(UDP)

> 版本: v1.0
> 日期: 2026-09-14
> 适用: CS96-beta 机型，`system:work_mode = 0`（连续原始直方图）
> 面向对象: 上位机软件开发者(按本文档实现 UDP 收包 → 组帧 → 波形/灰度显示)

---

## 1. 传输概要

| 项 | 值 | 说明 |
|---|---|---|
| 传输层 | UDP | 无连接, 不保证有序 |
| 数据目标 | `center_ip:center_data_port` | 默认 `192.168.110.15:50027`, 可被握手指令改写 |
| 板端源端口 | `local_data_port` | 默认 `65001` |
| **单个 UDP 数据报长度** | **固定 4105 B** | 9 B 协议头 + 4096 B 数据区, 同一机型所有包长度一致 |
| 字节序 | 小端 | ARM64 板端原生小端 |
| 帧组织 | 1 slot = 96 pixel = 24 个 UDP 包 | 见 §3、§4 |

**机型/模式识别**: 板端在指令通道(广播端口默认 `55000`)周期性广播, 广播包携带:

- `sn`：新版为 19 字节，优先发送完整 SN，读不到有效 SN 时发送 MAC 兼容标识。旧版为 18 字节。上位机按帧头长度选择对应字段偏移，见 [SN 码上位机读写开发指导](../SN码-上位机读写开发指导.md#31-推荐读取流程)。
- `work_mode`: `0` = RAW_MODE（连续，56×96）

上位机应在握手阶段先读取广播包确定机型与模式, 再选择对应的组帧策略, 不要依赖"收到的 UDP 包长度"来猜解析方式。

## 2. 单个 UDP 数据报格式

```
┌──────────┬───────────┬─────────────┬──────────┬───────────┬────────────────────┐
│  sof     │  frame_id │ slot_number │ seq_num  │ data_len  │  value             │
│  1 B     │  2 B      │  2 B        │  2 B     │  2 B      │  4096 B            │
│  0xAA    │  小端     │  小端       │  0~23    │  4096     │  4 个大点原始数据  │
└──────────┴───────────┴─────────────┴──────────┴───────────┴────────────────────┘
偏移: 0          1           3           5          7          9                4105
```

### 2.1 协议头字段(9 B, 1 字节对齐)

| 偏移 | 大小 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `sof` | 起始字节, 固定 `0xAA` |
| 1 | 2 | `frame_id` | 帧号, `0~65535` 循环递增; 见 §3 |
| 3 | 2 | `slot_number` | slot 号，`0~55` |
| 5 | 2 | `seq_num` | **包序号 `0~23`**, 用于 slot 内排序/丢包检测 |
| 7 | 2 | `data_len` | 数据区长度, 固定 `4096` |

### 2.2 数据区(4096 B)

- 4096 B = **4 个大点**连续排列, 每个大点 1024 B。
- 每个大点 = **512 个 uint16(小端)**, 即一个 pixel 的 512 桶直方图。
- 每个 uint16 为一个时间桶的计数值(16 bit; 有效位宽以 FPGA 输出为准, CS96 系列协议为低 12 bit 有效)。
- 第 `seq_num = n` 的包携带 `pixel(4n) ~ pixel(4n+3)`, 共 4 个大点。
- 一个 slot 的 96 个大点被切成 24 个包: `seq_num = 0~23`。

## 3. 帧结构

### 3.1 RAW_MODE(`work_mode = 0`，连续原始直方图)

| 项 | 值 |
|---|---|
| 一帧组成 | 56 个 slot × 96 个 pixel |
| `frame_id` | **每 56 个 slot 自增一次**(slot 55 → 0 时 `+1`) |
| `slot_number` | `0~55` 循环 |
| 一帧 UDP 包数 | 56 slot × 24 包 = **1344 包** |
| 一帧原始数据量 | 56 × 98304 B = 5,505,024 B(约 5.25 MB) |

上位机按 `frame_id` 分组, 即得到一张 **56×96** 的波形图集合(纵向 56 个 slot, 横向 96 个 pixel)。

## 4. 上位机组帧流程

```
收到 UDP 数据报
   │
   ├─ 1. 校验: 长度 == 4105 且 sof == 0xAA 且 data_len == 4096
   │        不满足 → 丢弃
   │
   ├─ 2. 按 (frame_id, slot_number) 归入对应 slot 缓冲
   │        每个 slot 缓冲: 24 个数据段(每段 4 个大点)
   │
   ├─ 3. 按 seq_num (0~23) 将数据段写入 slot 缓冲对应位置:
   │        seq_num=n → 写入 offset = n × 4096, 长度 4096
   │        收到重复 seq_num → 覆盖; 缺失 → 该 4096 B 保持/填 0
   │
   ├─ 4. slot 缓冲收齐后得到 96×512 的 uint16 波形数据:
   │        大点 i (0~95) 的 512 桶 = slot_buf[i × 1024 .. i × 1024 + 1024)
   │
   ├─ 5. 组帧:
   │        56 个 slot(0~55)拼成 56×96 波形图
   │
   └─ 6. 显示: 对每个 pixel 的 512 个桶取最大值(TOF 峰值) → 灰度值
```

### 4.1 未收齐处理(建议)

- 包级: 某个 `seq_num` 未到达时, 对应 4096 B 数据填 0(而不是整包丢弃), 避免整帧无效。
- slot 级: RAW_MODE 下某 slot 长时间未收齐, 该 slot 的 96×512 全部填 0。
- 帧级: 以 `frame_id` 变化作为换帧边界; 换帧时上一帧未收齐部分按上述规则填 0 后显示。
- 排序: 以 `seq_num` 为准, 不要依赖 UDP 到达顺序。

## 5. UDP 包长说明(重要)

1. **本机型直方图数据不做"按 MTU 靠拢"的应用层切分**, 生产者固定以 4096 B 数据 + 9 B 头组成一个协议包, 消费者整包发送。因此**每个 UDP 数据报长度恒为 4105 B**, 不存在同机型残包长度不一的问题。
2. 4105 B 超过以太网 MTU(1500 B), IP 层会自动分片(通常为 `1480 + 1480 + 1145` 的 IP 载荷), 由接收端内核重组后再交给应用层。因此:
   - 用 socket `recvfrom()` 收到的是**完整的 4105 B**, 长度固定;
   - 用抓包工具(tcpdump/Wireshark)看到的是 IP 分片长度(1500/1500/1165), **不要用抓包长度做解析**。
3. 若某个 IP 分片在网络中丢失, 整个 4105 B 数据报会被内核丢弃, 上位机表现为该 `seq_num` 丢包, 按 §4.1 填 0 处理。
4. 后续固件若改为应用层 MTU 分片(包长将不固定), 会另行在协议文档中说明并升级协议版本; 上位机可先用 `data_len` 字段做兼容(数据区长度始终以 `data_len` 为准)。

## 6. 常量速查

| 项 | 值 | 来源 |
|---|---|---|
| 协议头长度 | 9 B | `raw_protocal_data_packet_t` |
| 单个大点(pixel) | 512 × uint16 = 1024 B | `org_histogram_pixel_size` |
| 每包大点数 | 4 | `SLICES_HISTOGRAM_LEN / org_histogram_pixel_size` |
| 数据区长度 | 4096 B | `data_len` |
| UDP 数据报长度 | 4105 B | 9 + 4096 |
| 每 slot 大点数 | 96 | `lines_v`(垂直线数) |
| 每 slot 包数 | 24 | 96 / 4 |
| RAW_MODE 每帧 slot 数 | 56 | `lines_h` |
