# 设备模式切换：上位机与网页开发指导

文档版本：v1.2，2026-11-03。面向上位机、网页和设备 CGI 开发 Agent。

## 1. 本轮目标与交付边界

目标是让用户通过上位机或网页，查询设备实际状态，并切换设备当前允许的工作模式。客户端发起请求，设备上的 `lidar_mgrd` 执行切换及恢复；客户端不组织停进程、换文件或重启脚本。

本手册可以直接交给另一个 Agent 实施。HTTP 转发接口已在 221 的 RAM 环境部署，真实点云模式 2→1→2 切换通过，当前保留服务运行供上位机联调：

| 项目 | 当前状态 |
|---|---|
| `lidar_mgrd` 本地 UDS 查询、切换、子进程监督、有限次数恢复 | 已实现，主机模拟集成测试通过 |
| `lidar_mgrctl` 本地命令行客户端 | 已实现 |
| Beta/Gamma 按机型统一应用和用户态库 | 已实现并交叉编译 |
| 221 Beta 临时测试包 | 签名和文件校验通过，真实点云模式 2→1→2 切换通过 |
| HTTP 状态和切换接口 | 22 项主机测试及 Beta ARM64 构建通过；221 真实 lighttpd、UDS 和采集应用联调通过 |
| 上位机模式管理界面、网页模式管理界面 | **本轮交给对方 Agent 开发** |
| SN 从第四分区读取并在各服务统一使用 | 尚未实现；当前广播仍使用硬编码值 |
| Link Local 与统一网络配置服务对接 | 待与网络开发同事确认接口，不属于本轮实现 |
| 任意机型的直方图、点云、灰度自动硬件切换 | 尚未实现；受各平台配套约束 |
| 升级、重启、解除 FAULT、任务历史接口 | 当前守护进程不提供 |

```text
桌面上位机 ── HTTP ──┐
                    ├─ 设备原生 CGI ── Unix SOCK_SEQPACKET ── lidar_mgrd
设备网页 ─── HTTP ───┘                                      │
                                                            └─ 管理 you_see 和平台适配器
```

现有 `you_see_www/you_see_cgi/src/lidar_management/` 已新增两个原生 CGI，应直接复用。桌面端和网页端共用这些 HTTP 接口，避免再维护一套专用 UDP 管理协议。浏览器和另一台电脑上的桌面程序都不能直接访问雷达内部 UDS。

## 3. 工作模式与能力判断

协议枚举与显示文字可以固定；“某机型允许哪些模式”必须从设备状态动态读取。

| work_mode | 界面名称 | 所属 supported_modes 分组 |
|---|---|---|
| 0 | 连续原始直方图 | `histogram` |
| 1 | 原始点云 | `pointcloud` |
| 2 | 解算点云 | `pointcloud` |
| 3 | 灰度图 | `gray` |

可选模式为：已知枚举中，同时满足以下条件的模式。

```text
该模式编号存在于 validated_work_modes
并且该模式对应分组存在于 supported_modes
```

例如 221 测试配置返回：

```json
{
  "supported_modes": ["histogram", "pointcloud", "gray"],
  "validated_work_modes": [1, 2]
}
```

只允许选择 1 和 2。0、3、4 可以隐藏，或禁用并显示“当前设备未开放”。不要修改设备白名单来让按钮变得可点击，不要通过机型名称猜测支持范围。

`validated_work_modes` 是设备配置开放的测试/运行白名单，不等于一份独立的出厂验收证书。221 已完成本轮 1/2 切换验证，上位机界面、重新握手和解析器衔接仍需客户端验收。

当前 `actual_mode=-1` 表示未知、切换中或尚未确认，不表示某种新工作模式。客户端遇到未知枚举值时显示“未知模式（编号）”，禁止发送它，不要按默认点云处理。

## 4. 设备本地 UDS 契约：已经实现

### 4.1 传输

- 套接字类型：`AF_UNIX` + `SOCK_SEQPACKET`，不是 `SOCK_STREAM`，不是 UDP。
- 每个请求新建连接：connect → 立即 send 一条完整 UTF-8 JSON → recv 一条完整 JSON → close。
- 不使用长连接，不把 JSON 拆成多个数据包，不依赖换行分隔。
- 请求长度小于 1024 字节；接收缓冲区建议 8192 字节，检测截断和非法 JSON。
- 服务接受连接后只短暂等待请求，客户端 connect 后应立即发送，不能先等待服务问候消息。
- 一次 UDS 调用设置总超时；建议 10 秒，不一直阻塞 CGI。
- 套接字路径由设备本地受信任配置提供，**不能从 HTTP 请求传入**。

221 测试路径：`/tmp/beta-test/control.sock`。

产品配置示例路径：`/run/lidar/control.sock`，这只是配置示例，不表示当前设备已经部署该路径。

服务限制套接字为 0600，并检查对端 UID 与自身 UID 相同。当前测试环境为 root，须确认 CGI 有实际连接权限。不要用 `chmod 777` 绕过检查；正式权限划分另由设备端设计本地转发权限，不能盲目把整个 Web Server 提权。

### 4.2 现有请求

```json
{"op":"status"}
```

```json
{"op":"switch","work_mode":1}
```

当前只支持这两个操作。没有 `start`、`stop`、`reboot`、`upgrade`、`set_sn`、`set_ip`、`reset_fault` 或按任务 ID 查询的操作。

### 4.3 状态响应示例

下面是便于开发的示例，不是 221 的实时记录：

```json
{
  "code": 200,
  "message": "状态",
  "model": "CS96-beta",
  "operation_id": "11111111111111111111111111111111",
  "version": null,
  "simulation": false,
  "phase": "COMMITTED",
  "confirmed_mode": 2,
  "actual_mode": 2,
  "desired_mode": 2,
  "error": "",
  "pid": 1234,
  "initialized": true,
  "pipeline_verified": true,
  "supported_modes": ["histogram", "pointcloud", "gray"],
  "validated_work_modes": [1, 2]
}
```

| 字段 | 含义与显示要求 |
|---|---|
| `code` | 本次请求结果；本地 JSON 字段，还不是 HTTP 状态 |
| `model` | 设备管理配置与软件包匹配的机型，不是 SN |
| `operation_id` | 当前操作关联标识；用于关联轮询，不是可重试令牌，也不是任务历史索引 |
| `version` | 包的版本标签；开发包可能为 null，显示“未标记版本” |
| `simulation` | true 时必须明显显示“模拟环境”；由设备返回，客户端不能请求关闭签名验证 |
| `phase` | 当前公开执行阶段，见后文 |
| `confirmed_mode` | 最后确认成功的模式；不是切换期间的实际输出模式 |
| `actual_mode` | 当前确认的运行模式；-1 显示“切换中/未确认” |
| `desired_mode` | 守护进程此刻正在争取的模式；回滚时会变成恢复目标 |
| `error` | 最近失败或恢复原因，可能在 COMMITTED 时仍非空 |
| `pid` | 采集进程诊断信息，不能单凭非零判定采集正常 |
| `initialized` | 应用报告事件循环初始化完成 |
| `pipeline_verified` | 应用报告连续观察到符合检查条件的数据包，不等于完整帧验证、上位机收到数据或硬件全面验收 |
| `supported_modes` | 包中包含的模式分组 |
| `validated_work_modes` | 配置开放的具体模式编号 |

不应因为 `pid > 0`、`initialized=true`、HTTP 200 或 JSON `code=200`，就单独显示“切换成功”。

### 4.4 原生错误结果

| code | 语义 | 客户端行为 |
|---|---|---|
| 200 | 状态读取成功，或者已经处于目标模式 | 根据 phase 和模式字段显示；不代表新切换完成 |
| 202 | 已受理切换 | 保存本次目标及 operation_id，继续轮询 |
| 400 | 请求格式错误 | 报错，不重试写请求 |
| 409 | 非 COMMITTED 阶段，已有操作或初始化进行中 | 刷新状态；不排队、不自动重新提交 |
| 422 | 未开放、未包含，或软件包验证失败 | 展示 message；不能都归类为“模式不支持” |
| 500 | 意图持久化失败等入口错误 | 不当作受理；重新查询当前状态，原采集可能仍运行 |
| 503 | 当前为 FAULT，拒绝切换 | 仍允许读取状态；需人工检查 |
| 501 | 未实现的 op | 不调用其他脚本代替 |

重要：`status` 查询到 FAULT 时，本次查询仍返回 code=200。FAULT 在 `phase` 字段中表达。不要把正常查询到的设备故障误报为“设备离线”。

## 5. HTTP 桥接契约：已在 221 部署联调

本轮使用直接 CGI 路径，避免依赖尚未配置的 URL 重写。

| 方法与路径 | 行为 |
|---|---|
| `GET /cgi-bin/lidar_status.cgi` | 发送本地 `{"op":"status"}`，原样返回管理状态 |
| `POST /cgi-bin/lidar_switch.cgi` | 接收 `{"work_mode":1}`，转为本地 switch 请求 |

这两个 CGI 的源码、构建和主机测试已在 `you_see_cgi/src/lidar_management/` 补齐，ARM64 产物在 `you_see_cgi/build/`，已安装到 221 的 `/www/cgi-bin/`。桥接配置位于 `/etc/lidar/http-bridge.json`，连接 `/tmp/beta-test/control.sock`。上位机 Agent 直接复用，不需要重复开发 CGI。以上文件仅在 RAM 中，设备重启后需由研发重新部署。

### 5.1 桥接实现与接入要求

1. 使用 C/C++ 原生 CGI，复用工程已有 JSON 库和构建方式，不要求板端安装 Python、Node.js 或新增常驻 Web 服务。
2. 直接连接 UDS；不要用 shell、`system()`、`popen()` 或 SSH 调用 `lidar_mgrctl`。
3. GET 只查询；模式切换只接受 POST 和 `application/json`。请求体设置小上限，例如 256 字节。
4. POST 仅接受一个 `work_mode` 字段，值为整数 0～4；拒绝布尔、非整数数值（如 1.5）、字符串、未知字段和任何命令/路径参数。
5. HTTP `Content-Length`、输入长度和 JSON 解析错误必须处理；不把客户端提供的 `op` 原样转发。
6. UDS 成功响应保留原 JSON 字段，根据 `code` 输出真正 HTTP 状态；CGI 要发送 `Status:`，不能所有结果都 HTTP 200。
7. 所有响应设置 `Content-Type: application/json; charset=utf-8` 与 `Cache-Control: no-store`。
8. UDS 总超时建议 10 秒，HTTP 客户端超时建议 12 秒。202 之后异步轮询，不在单次 POST 中等待整次切换。
9. 复用现有访问控制；写操作要校验身份和请求来源。当前 CGI 对有 Origin 的 POST 做同源校验（不匹配返回 403），不提供通配 CORS；它不替代部署环境的用户认证。若现有工程尚无认证，明确限定为受控测试网络，不能宣称已经具备生产访问控制；不要新增允许任意站点写操作的 CORS 配置。
10. 本地套接字路径来自设备端配置。221 使用 `/tmp/beta-test/control.sock`；不能为了兼容另一个路径偷偷启动第二个管理服务。

### 5.2 状态映射

原生返回的 200、202、400、409、422、500、501、503，通常对应相同 HTTP 状态，保留 JSON 结果。状态查询即使 `phase=FAULT`，也应是 HTTP 200。

桥接自身失败时，使用下面的区别，避免伪造管理进程状态：

| HTTP 状态 | 桥接问题 |
|---|---|
| 400 | JSON、长度、字段或模式值不合法 |
| 403 | POST 的 Origin 与请求 Host/方案不匹配 |
| 405 | 方法不支持，附正确 Allow 头 |
| 408 | 请求正文读取超时，尚未向管理服务发送操作 |
| 413 / 415 | 请求体过大 / 媒体类型不支持 |
| 503 | UDS 不存在、连接被拒绝或本地权限不匹配 |
| 504 | 等待管理服务响应超时 |
| 502 | UDS 响应截断、非法 JSON、字段结构不符合协议 |

桥接错误示例：

```json
{"code":503,"message":"设备管理服务不可用","source":"bridge"}
```

桥接错误没有可信的 phase 或模式字段，不要填充旧值伪装成设备实时状态。界面可以保留最后一次状态，但必须标注“非实时”。

### 5.3 上位机和网页如何调用

221 当前可直接使用以下命令；重启后先确认 RAM 部署仍在：

```bash
curl -i http://10.42.0.221/cgi-bin/lidar_status.cgi
curl -i -H 'Content-Type: application/json' \
  -d '{"work_mode":1}' http://10.42.0.221/cgi-bin/lidar_switch.cgi
```

网页使用同源相对路径；桌面端把设备地址配置为连接目标，不把地址或 SSH 凭据写死进业务逻辑。处理 fetch/HTTP 客户端的非 2xx JSON，不能只显示通用网络错误而丢掉管理服务的 message。

尚未安装桥接层时，只有本机 SSH 命令行可用。SSH 命令仅用于研发人工联调，不是客户端产品的后备传输。

## 6. 状态显示与成功判定

### 6.1 公共阶段

| phase | 显示文字 | 是否允许切换 |
|---|---|---|
| STOPPING | 正在停止当前采集应用 | 否 |
| PREPARING | 正在准备目标运行环境/执行平台适配 | 否 |
| VERIFYING | 正在启动并验证采集流水线 | 否 |
| COMMITTED | 当前模式已确认 | 满足能力与连接条件时允许 |
| FAULT | 故障，需要检查 | 否 |
| 未知值 | 未识别设备阶段 | 否，继续查询并记录诊断 |

PENDING、RECOVERING、STOPPED 是持久化日志中的值，当前不作为独立的公开 phase。自动恢复时仍可能看到 STOPPING/PREPARING/VERIFYING，不能等待一个永远不会出现的公开 ROLLING_BACK。

服务没有真实百分比和预计剩余秒数。界面用阶段指示器或不定进度条，不显示虚构的 30%/80%。phase=COMMITTED 也不代表“激光扫描状态”：若要显示扫描、空闲或握手状态，继续使用原采集协议的相应信息。

### 6.2 一次切换的客户端算法

```text
读取最新状态，计算可选模式
确认 phase=COMMITTED，目标在能力交集内
保存用户请求目标 requested_mode、当前模式、当前 operation_id
发送一次 POST，禁止重复点击

若返回 200 且确认已在目标模式：按响应及最新状态显示，不创建新任务
若返回 202：保存响应 operation_id，进入切换轮询
若返回 409/422/500/503：显示拒绝原因并刷新状态，不当作已受理
若 POST 超时/断网：标为“请求结果待确认”，只查询，不自动重发 POST

轮询期间：
  若 operation_id 改变：原操作结果无法可靠关联，停止判定原操作成功，重新同步
  若 phase 为中间阶段：更新阶段，不发送新切换
  若 phase=FAULT：失败，显示 error
  若 phase=COMMITTED：
    actual_mode 与 confirmed_mode 均等于 requested_mode，且 error 为空 → 本次切换成功
    模式等于 requested_mode 但 error 非空 → 已达到目标但发生异常/恢复，显示告警
    actual_mode 不等于 requested_mode → 目标切换未成功；若恢复到旧模式，明确显示回滚结果
```

不能用 `desired_mode == actual_mode` 作为本次成功判据，因为恢复时 desired_mode 会被改为旧模式。不能丢掉本地保存的 requested_mode。

例如用户请求 1，恢复后的响应可能是：

```json
{
  "code":200,
  "phase":"COMMITTED",
  "confirmed_mode":2,
  "actual_mode":2,
  "desired_mode":2,
  "error":"数据验证超时"
}
```

这应显示“切换到原始点云失败，已恢复解算点云”，而不是“切换成功”。上面只节选相关字段，完整样例见 examples 文件。

`operation_id` 当前不是幂等键，没有请求去重或任务历史查询接口，守护进程重启后标识也会变化。客户端刷新后若丢失请求上下文，只显示当前状态和错误，不伪造“上一次请求成功”的结论。

### 6.3 轮询与断线

- 正常页面可每 2 秒查询；切换中建议每 500 毫秒查询。每个设备最多一个正在进行的查询，上一请求未结束不启动下一次。
- 页面关闭或设备选择改变时停止原轮询，避免旧设备响应更新新设备界面。
- 查询响应应串行或带客户端序号，拒绝迟到响应覆盖新状态。
- 一轮客户端观察超过 60 秒仍未确定结果，可显示“等待超时，请查看设备状态”，但不能据此宣称设备已回滚，也不能自动重启设备或重新提交。
- 连接失败时显示“管理状态不可用/请求结果待确认”；不要假定设备已重启或该请求已取消。
- 多客户端竞争由设备端裁决；收到 409 后观察服务当前操作，不自动排队覆盖其他人的目标。

## 7. 原有上位机数据连接怎样衔接

模式管理 HTTP 不替代原广播、采集握手、心跳与 UDP/TCP 数据协议。

上位机发起切换前暂停当前流的解码和显示，保留已有协议正常停止/断开流程；如果该流程与设备适配存在未确认依赖，先与嵌入式侧联调，不发送额外的未定义停止指令。

切换过程中应用会重启，旧采集会话不能假定继续有效。模式提交完成后：

1. 通过原发现机制重新定位或确认设备地址。
2. 重新完成采集握手，配置本次需要的接收端口。
3. 依据已确认的模式选择对应数据解析器，清空旧帧、分片及超时缓存。
4. 收到实际有效数据后，再显示“上位机数据接收正常”。

原始点云与解算点云解析器不同。服务的 `pipeline_verified=true` 不能代替上位机自己的数据解析和接收统计。网页只负责切换时，不需要模拟采集握手或承担雷达数据传输。

嵌入式侧已统一配置读写路径：握手、回波和坐标参数写回本次启动实际加载的 `YS_CONFIG_PATH`，不会写回系统默认主配置。真实配置加载和参数写回回归已通过；本轮 221 握手前后 `/etc/ys_conf.ini` 校验值一致。标定仍使用原有标定文件，不属于本轮修改范围。

## 8. SN 与后续 Link Local 的兼容设计

当前管理响应没有 SN、identity 或网络状态字段；客户端显示“SN 尚未接入管理接口”，不能从字段缺失直接断定设备未烧录 SN。

221 的预期真实 SN 是 `CS96000B0126100003`，但未写入第四分区，现有采集广播仍有硬编码 SN。这个预期值只作为人工测试记录，不能写进 UI 当作设备读回结果，也不能据旧广播建立可靠的多设备唯一身份绑定。

本轮先支持人工选择设备 IP 的单台定向测试。IP 是当前连接位置，不作为永久设备身份。SN 统一接入后，再以真实 SN 关联设备记录，地址作为可变属性。

为网络服务留出客户端抽象：设备身份、当前连接地址、管理 HTTP、采集数据会话分别管理。地址变化时要重新定位和握手，不能认为 SN 相同就永远是原 IP。不要在本轮实现按 SN 推导 IP、配置 Link Local、静态 IP 写入或修改系统网卡。

## 9. 221 实机联调步骤

### 9.1 前提

- 当前测试目录 `/tmp/beta-test` 在设备重启后会消失；先确认文件仍在。
- 当前已保留管理服务和模式 2 采集运行；先查询状态，正常时直接开展上位机测试，不重复执行 start。
- 仅在重启或人工停止后通过 SSH 准备测试会话。新 UI 不负责执行 test.sh、启动守护进程或改变白名单。
- 当前包只允许 work_mode=1/2。所有网络写操作和 SN 写入均不属于本轮。

```sh
cd /tmp/beta-test
sh test.sh check
sh test.sh start
sleep 3
sh test.sh status
```

等待原生命令行确认 COMMITTED、actual_mode=2，作为 HTTP 接入的基线。若此处失败，先排查嵌入式侧，不继续把问题归因于前端。

### 9.2 HTTP 与界面联调

1. 当前 221 CGI 已部署，直接检查 HTTP 可达性；设备重启后再按模块 README 恢复 RAM 部署。不修改 238，不更新 Flash 启动项。
2. 配置桥接连接 `/tmp/beta-test/control.sock`，原生命令行与 HTTP 查询结果应一致。
3. 从界面请求模式 1，观察异步状态、最终模式，再验证原始点云的数据握手与解析。
4. 请求模式 2，验证解算点云恢复。
5. 验证重复点击不会重复提交，不支持模式不会被界面发送，后端也能拒绝手工构造的非法请求。
6. 故障、恢复失败、迟到 token 等异常主要在主机模拟环境验收，不能靠在真机乱改内核模块或 FPGA 制造故障。

当前为后续上位机联调保留测试服务运行。只有结束整个测试环境时，再由人工恢复原应用：

```sh
cd /tmp/beta-test
sh test.sh logs
sh test.sh restore
```

重启可以恢复原有启动流程，但会删除 RAM 内测试包和日志。先保存日志再重启。test.sh 每次 start 创建新会话，因此跨 start 的行为不是 Flash 持久化或断电恢复的验收。

## 10. 验收清单

| 场景 | 必须达到的结果 |
|---|---|
| 正常读取状态 | 模式、阶段和版本正确，version=null 不伪造版本 |
| 仅开放点云 1/2 | 不允许发送 0/3/4；灰度不因“包包含”而启用 |
| 202 受理 | 显示切换中，不立即提示成功 |
| 同一模式请求返回 200 | 不虚构新任务、不额外重启应用 |
| 目标切换成功 | 目标编号、actual_mode、confirmed_mode 与任务关联均正确 |
| 自动回滚到旧模式 | 明确显示目标失败和恢复结果，不被 COMMITTED 误导 |
| FAULT 状态查询 | HTTP 200，界面显示设备故障，不误报离线 |
| 多客户端或重复点击 | 单客户端只发一次；外部竞争返回 409，不自动重试写请求 |
| 管理服务不在线/权限不符 | HTTP 503，界面显示管理服务不可用 |
| 桥接不存在 | 显示管理接口未部署，不调用旧 CGI 后备 |
| POST 结果超时 | 只查询确认，不自动重复发送切换 |
| operation_id 改变 | 不把其他操作或重启后的结果归属于原请求 |
| 页面刷新/切换设备 | 旧响应不污染当前界面，无请求上下文时不伪造历史结果 |
| 模拟环境 | 明显标识，不能把模拟测试当作 221 硬件验收 |
| SN 尚未接入 | 不写死、不从硬编码广播冒认真实身份 |
| 新模式生效后接收数据 | 重新握手、切换解析器、清空旧帧缓存 |
| 请求非法类型 | 布尔、字符串、非整数数值及额外字段被桥接拒绝 |
| 未知阶段或未来字段 | 未知阶段禁用写操作，未知附加字段可忽略 |

桥接需要能在主机环境用可配置 UDS 路径连接模拟服务。可参考现有 `scripts/test_lidar_mgrd.py`，但不得把测试中的模拟硬件脚本安装成真实硬件适配器。
