## 实测结果

| 场景 | 结果 |
|---|---|
| 包文件、测试签名、固定内核模块标识校验 | 全部通过，未使用 simulation 绕过验证 |
| HTTP 查询与本地 lidar_mgrctl 对照 | 模式和最终健康状态一致 |
| 模式 2→1 | HTTP 202 受理，约 3.2 秒后 COMMITTED，actual_mode/confirmed_mode 均为 1 |
| 模式 1→2 | HTTP 202 受理，约 3.2 秒后 COMMITTED，actual_mode/confirmed_mode 均为 2 |
| 切换时再次提交 | HTTP 409，保持原操作标识 |
| 已在模式 2 时再请求 2 | HTTP 200，PID 和操作标识不变 |
| 请求未开放的模式 0 | HTTP 422，原采集保持运行 |
| 管理服务未启动时查询 | HTTP 503，source=bridge |
| 方法错误 | HTTP 405，Allow 正确 |
| 非 JSON、布尔模式、跨来源、超长正文 | 分别为 415、400、403、413 |
| HTTP 响应头 | JSON UTF-8、真实状态码、正确 Content-Length、no-store、nosniff |

为验证切换后的数据会话，再次执行 2→1→2，每种阶段按现有协议握手并接收数据：

| 阶段 | 收到并校验的包数 | 每包长度 | 校验内容 |
|---|---|---|---|
| 初始模式 2 | 1000 | 1266 字节 | 来源、面号、总槽数、槽号、单回波和坐标类型 |
| 切换后的模式 1 | 1000 | 1561 字节 | 来源、0xAA、数据长度、槽号与原始 SLOT 槽号一致 |
| 切回模式 2 | 1000 | 1266 字节 | 与初始模式 2 相同 |

每个阶段样本包含 800 种槽号；握手响应通过 CRC16/CRC32 校验。握手后完成 1000 包接收耗时约 1～3.1 秒，客户端需持续心跳并给予合理接收等待时间。以上证明本轮采样的结构和模式对应，不等于完整帧无丢包、点云精度或长时间稳定性验收。

主机端 HTTP 桥接 22 项测试、管理进程 13 项测试通过。新增运行配置回归使用真实加载及回波/坐标写回函数并启用 AddressSanitizer，验证临时文件回写、系统默认路径隔离、相对及超长路径拒绝。

## 本轮修复

应用启动时缓存实际加载的配置路径；握手、回波和坐标参数写回此路径，修复读取运行配置却写回 `/etc/ys_conf.ini` 的问题。新增 INI 项没有注释时，原序列化代码会解引用空指针，本轮补齐判空并通过真实写回回归。实机握手已写入临时运行配置，系统主配置 SHA256 保持原值。

没有修改采集协议和数据发送路径。守护进程仍不承载 HTTP，CGI 直接通过 UDS 转发。

## 上位机现在可以执行的操作

```bash
curl -i http://10.42.0.221/cgi-bin/lidar_status.cgi

curl -i -H 'Content-Type: application/json' \
  -d '{"work_mode":1}' http://10.42.0.221/cgi-bin/lidar_switch.cgi

# 继续查询，确认目标模式和健康状态，不把 202 当作切换成功。
curl -i http://10.42.0.221/cgi-bin/lidar_status.cgi

curl -i -H 'Content-Type: application/json' \
  -d '{"work_mode":2}' http://10.42.0.221/cgi-bin/lidar_switch.cgi
```

当前保留测试服务运行，无需再次 start。不要点击旧网页的旧切换按钮，它们仍可能执行原 Flash/重启脚本。网页和上位机按[开发指导手册](设备模式切换-上位机与网页开发指导.md)接入新 CGI。

只有结束整个测试环境、需要恢复原应用时，才在设备上执行：

```sh
sh /tmp/beta-test/test.sh restore
```

restore 会停止本轮管理服务，HTTP 随后返回管理服务不可用；它不会自动删除新 CGI。重启恢复原有启动流程，同时清除 RAM 测试文件与日志，请先取回日志。
